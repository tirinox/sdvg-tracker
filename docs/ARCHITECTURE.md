# Архитектура СДВГ-трекера

Аналог Tiimo для людей с СДВГ. Один пользователь, клиенты iOS и Web, backend на Python.
Без трекера настроения в MVP; из ИИ — только подбор эмодзи небольшой моделью на сервере (3.4).

## 1. Принципы

- **Local-first.** Каждый клиент хранит полную копию данных в локальной БД и работает только с ней.
  Сервер — точка синхронизации и бэкап, а не источник истины для UI.
- **Производные данные не храним.** Стрик, счётчики, число переносов, heatmap вычисляются из фактов.
  Хранимый счётчик, увеличенный на двух офлайн-устройствах, неизбежно разъедется.
- **Детерминированные ID** там, где два устройства могут независимо создать «одно и то же»
  (отметка рутины за день, автоперенос за день) — дубли сливаются в одну запись.
- **Неизменяемые сущности** (версии рутин, переносы) — только добавление, конфликтов нет.

```
┌─────────────┐        ┌──────────────┐
│ iOS (Swift) │        │ Web (Vue/PWA)│
│ SQLite/GRDB │        │  IndexedDB   │
│  + outbox   │        │   + outbox   │
└──────┬──────┘        └──────┬───────┘
       │  POST /api/sync (push+pull) │
       └──────────┬──────────────────┘
           ┌──────▼──────┐
           │  FastAPI    │
           │ SQLite (WAL)│  docker compose
           └─────────────┘
```

## 2. Время и дни

- Даты задач — **локальные** `YYYY-MM-DD`, время — локальное `HH:MM`, без таймзоны.
- **Логическое «сегодня»** = `now − day_start_hour` (по умолчанию 4:00): в 1 ночи ещё «вчера».
- **Конец дня** — `day_start_hour` следующей даты, а не полночь; «сегодня» и время считаются по часам
  и таймзоне устройства. У заголовков «Сейчас» и «Сегодня» — обратный отсчёт до конца дня:
  за час жёлтый, за полчаса красный (`domain-fixtures/day_end.json`).
- Части суток: `morning` / `day` / `evening`, границы настраиваются (по умолчанию 6 / 12 / 18).
- Тип времени задачи `time_kind`: `none` (в любое время) | `part` (часть суток) | `exact` (точное время).
- Порядок дня: «в любое время», затем Утро → День → Вечер; внутри — сначала по приоритету
  (высокий → обычный → низкий), затем без точного времени по `sort_key` (дробный индекс), с точным — по времени
  (`domain-fixtures/item_order.json`).

## 3. Модель данных

### 3.1. Регулярные задачи (рутины)

Рутина — это **шаблон**. Экземпляры на день не хранятся, а вычисляются.

| сущность | поля | синхронизация |
|---|---|---|
| `routine` | `id`, `sort_key` | LWW по полям |
| `routine_version` | `id`, `routine_id`, `effective_from`, `title`, `emoji`, `color`, `time_kind`, `part_of_day`, `time`, `duration_min`, `priority`, `weekdays` (битовая маска, по умолчанию все), `archived` | неизменяемая |
| `routine_check` | `id = uuidv5(routine_id + date)`, `routine_id`, `date`, `status` (`done` / `skipped`), `done_at`, `snapshot` {title, emoji, color, time_kind, part_of_day, time} | LWW по полям |

- **Рутины дня D**: для каждой рутины берём версию с максимальным `effective_from <= D`
  (при равенстве — с большим HLC). Если она не `archived` и день недели входит в `weekdays` — рутина есть в дне D.
- **Изменение** создаёт новую версию с `effective_from = сегодня`
  (или завтра, если сегодня рутина уже отмечена). Прошлые дни не меняются.
- **Удаление** — новая версия с `archived = true`. История остаётся.
- **Рутины не переносятся.** Невыполненная рутина прошлого дня — пропуск в истории.
- `skipped` — осознанный пропуск (болезнь и т.п.), не ломает стрик.
- `snapshot` фиксирует, как рутина выглядела в момент отметки.

### 3.2. Разовые задачи

| сущность | поля | синхронизация |
|---|---|---|
| `task` | `id` (UUIDv7), `title`, `notes`, `emoji`, `color`, `date` (null = «Входящие»), `first_date`, `time_kind`, `part_of_day`, `time`, `duration_min`, `priority`, `deadline_date`, `deadline_time`, `done_on`, `deleted`, `sort_key` | LWW по полям |
| `task_move` | `id = uuidv5(task_id + from_date)`, `task_id`, `from_date`, `to_date`, `kind` (`auto` / `manual`) | неизменяемая |

- **Автоперенос.** При старте клиента и при смене логического дня: для каждой невыполненной задачи
  с `date < today` создаётся **по одной `task_move` на каждый пропущенный день**, затем `date = today`.
  Детерминированный ID — два устройства создадут одинаковые записи, двойного счёта нет.
- **Ручной перенос** («на завтра») — `task_move` с `kind = manual`.
- **Счётчик переносов** = `count(task_move where task_id = …)`.
- **Дедлайн** не сдвигается переносами.
- **Копия** (в деталях задачи: на завтра или на любой день с сегодняшнего) — новая задача с тем же
  содержимым: без переносов и отметки о выполнении. Дедлайн, прошедший к дню копии, не копируется.

Уровни внимания по переносам (пороги настраиваемые):

| переносов | вид |
|---|---|
| 0 | ничего |
| 1–2 | серый бейдж `↻N` |
| 3–5 | оранжевый бейдж и обводка |
| 6–9 | красный, лёгкая пульсация, поднимается выше в списках |
| 10+ | красный + подсказка «Застряла? Разбить / во Входящие / удалить» |

Индикатор дедлайна: 🟢 ок · 🟡 скоро (≤ 2 дней или прошло > 80 % срока от создания) · 🟠 сегодня · 🔴 просрочен.

### 3.2.1. Приоритет

`priority` у задачи и у версии рутины: `low` / `normal` / `high`, по умолчанию `normal`. Поле появилось
позже остальных: у старых строк его нет, они читаются как `normal`. Приоритет рутины меняется, как любое
её поле, — новой версией.

- **Высокий**: полоса слева, метка «!! важно» и пульс — кольцо, раз в 3 с расходящееся от строки и гаснущее, —
  всё в цвете иконки задачи. Пульсы соседних строк сдвинуты по фазе; у выполненных и при «уменьшении движения»
  пульса нет.
  Высокий приоритет поднимается выше в списках, а на «Сейчас», когда пришло её время, — выше даже
  застрявшей задачи.
- **Низкий**: заголовок приглушён, подпись «↓ не срочно», в списках — в конце своей части дня.
- Красный и оранжевый остаются за дедлайнами и переносами: приоритет — выбор человека, а не тревога.

### 3.3. Настройки

`settings` — синхронизируемый синглтон (LWW по полям): `day_start_hour`, границы частей суток,
пороги внимания, `streak_min_done` (по умолчанию 1), `routine_warn_below` — порог выполняемости рутин
в процентах (по умолчанию 50, 0 — не предупреждать).

### 3.4. Эмодзи и цвет

`emoji` — строка; `color` — индекс в палитре (~12 цветов), одинаковой на iOS и Web и адаптированной
под тёмную тему. Отображение: цветной кружок с эмодзи.

Эмодзи к названию подбирает сервер (токен тот же, что у sync):

```
POST /api/suggest-emoji
{ "text": "Записаться к стоматологу", "limit": 5 }
→ { "suggestions": [ { "emoji": "🦷", "score": 0.96 }, { "emoji": "📝", "score": 0.89 }, … ],
    "pick": "🦷" }
```

- Модель — `multilingual-e5-small` (int8 ONNX, ~120 МБ, onnxruntime на CPU, единицы мс на запрос).
  Название и описания эмодзи — векторы; балл эмодзи — косинус до ближайшего из его описаний.
- Описания: имя и ключевые слова из Unicode CLDR (`backend/app/emoji/catalog.tsv`, ~1200 эмодзи;
  без оттенков кожи и мужских/женских копий, а цифры-кнопки, циферблаты и большинство флагов
  совпадают со словами задач случайно) и фразы задач (`aliases.txt`: CLDR знает «зуб», задача —
  «записаться к стоматологу»). На 50 новых названиях (`backend/tests/emoji_titles.txt`) фразы
  подняли долю подходящего первого эмодзи с 48 до 74 %, подходящего в первой тройке — с 64 до 90 %.
- `pick` — эмодзи, который клиент ставит без вопроса: первый, если его балл ≥ 0,9, иначе `null`.
  Порог зависит от модели, поэтому решает сервер. На `emoji_titles.txt` он пропускает 32 названия
  из 50, у 27 из них эмодзи подходит; промахи вроде «Кружки клеить на стулья» → 🛏️ ниже 0,88.
- Модель грузится в фоне при старте, векторы описаний кешируются рядом с БД. Пока она грузится
  или если её нет — `503`: клиент просто не показывает подсказки. Название — в теле запроса,
  не в URL: URL попадают в логи.
- Клиенты (веб и iOS): в редакторе задачи и рутины под кругом — ряд «Подходят» (тап выбирает);
  у новой записи круг сам берёт `pick`, пока эмодзи не выбран руками. Задача из быстрого добавления
  без эмодзи получает `pick` после создания, если к ответу эмодзи всё ещё нет. Без сети — ничего.

## 4. Производные данные

- **Выполнено за день D** = разовые задачи с `done_on = D` (включая удалённые) + `routine_check` со `status = done` за D.
- **Стрик** — число дней подряд, где выполнено ≥ `streak_min_done`, или все запланированные рутины `skipped`.
  Незавершённое сегодня стрик не обнуляет.
- **Счётчики**: сегодня «выполнено / всего», всего выполнено за всё время.
- **Выполняемость рутины** — доля её дней за последние 30 (включая сегодня), когда она сделана, в целых
  процентах. Не раньше первого запланированного дня, когда рутина сделана: новая рутина не начинает с провала,
  а заброшенная давно опускается до 0 %. Считаются только дни, где рутина есть по своей версии
  (архивные и чужие дни недели не в счёт). `skipped` не считается вовсе, день без отметки — пропуск,
  сегодня — только когда уже сделано. Ниже `routine_warn_below` рутина пропускается: в списке рутин
  процент становится предупреждением, в строке рутины на экранах дня — метка `⚠︎ 40 %`, в редакторе —
  откуда процент («сделано 5 из 8 дней с 5 сент»). Правило — `domain-fixtures/routine_adherence.json`.
- **Heatmap** (как на GitHub): 53 недели × 7 дней, 5 уровней; пороги уровней — квантили личной истории.
  Тап по клетке — список задач дня.
- **Подсказки названий.** Пока набирается новая задача, под полем — до 5 названий прошлых задач
  (одинаковые без учёта регистра, знаков и ё/е — одна подсказка). Сначала те, что начинаются с набранного,
  затем совпадения по началу слов в любом порядке («слова» → «Японский: слова»); внутри — по частоте
  с затуханием (вес использования × 0.5 каждые 30 дней). Подсказка несёт эмодзи, цвет и длительность
  последнего раза: в быстром добавлении тап сразу создаёт задачу, ↖ вставляет название для правки.
  Названия, которые сейчас заняты (см. ниже), не подсказываются.
  Правило — `domain-fixtures/title_suggestions.json`.
- **Повторы названий.** Название новой задачи сверяется (так же нормализованным) с открытыми задачами
  на любой день и во «Входящих», с рутинами и с тем, что сделано сегодня. Совпадение с открытой задачей
  или рутиной — задача не создаётся, под полем «Такая задача уже есть» и «Открыть». Если всё с этим
  названием сделано сегодня, предлагается добавить с номером: «Выдать ВИП статус» → «Выдать ВИП статус (1)»,
  «… (1)» → «… (2)» — следующий после наибольшего номера среди перечисленного. Пока название набирается,
  под полем — до двух похожих открытых: у них общих триграмм слов (как в pg_trgm) больше половины —
  другой порядок слов, окончание, опечатка. Похожие только предупреждают. Правило — `domain-fixtures/title_check.json`.

## 5. Домашний экран «Сейчас»

Топ 5–7 задач (разовые + рутины сегодняшнего дня) по баллу:

```
score = now_score + deadline_score + postpone_score
now_score:      точное время в окне [−30 мин, +60 мин] → 100; текущая часть суток → 50
deadline_score: просрочен 90 · сегодня 80 · скоро 60
postpone_score: min(переносы × 8, 70)
```

Порядок: сначала по приоритету, затем по баллу. Задачи с высоким приоритетом попадают в топ и с нулевым
баллом, но только когда их время пришло: без времени — всегда, часть суток — с её начала, точное время —
за 30 минут (`domain-fixtures/time_started.json`). До этого важная задача считается обычной: попадает
в топ только по баллу (дедлайн, переносы) и наверх не поднимается. Если отобранных меньше 5, список
добирается следующими по порядку дня (`domain-fixtures/now_pick.json`).

Каждая карточка показывает причину: `⏰ через 15 мин`, `🔥 дедлайн завтра`, `↻ 7 переносов`.

## 6. Синхронизация

### 6.1. Часы

Каждое изменение поля помечается **HLC** (hybrid logical clock): строка
`"{ms:013d}-{counter:04d}-{node_id}"`, лексикографически сортируемая. Для каждой строки хранится
`clocks: {field: hlc}`. Слияние — по каждому полю побеждает максимальный HLC.

### 6.2. Протокол

```
POST /api/sync
Authorization: Bearer <token>
{ "cursor": 1842,
  "changes": [ { "entity": "task", "id": "…",
                 "fields": { "title": "…" }, "clocks": { "title": "…" } } ] }
→
{ "server_id": "…", "cursor": 1857, "has_more": false,
  "changes": [ …всё, что изменилось на сервере после 1842… ] }
```

- Сервер ведёт монотонный `server_seq`; каждое изменение строки получает новый seq. Pull: `seq > cursor`.
- Push идемпотентен (слияние по HLC), всё в одной транзакции (`BEGIN IMMEDIATE`).
- Изменения проверяются по JSON Schema из `shared/schema`; одно невалидное — `422`, не применяется ничего.
  Часы дальше суток в будущем отклоняются: устройство со сбитыми часами иначе выигрывало бы все конфликты.
- `server_id` — набор данных: меняется, только когда базу опустошают или заменяют. Клиент с другим
  `server_id` получает `409` и ставит синхронизацию на паузу, пока пользователь не выберет:
  взять данные сервера или объединить с ними свои. Молча чужие данные не сливаются.
- `epoch` меняется при восстановлении из бэкапа: сервер отвечает `rewind`, клиент отправляет все свои строки —
  так к серверу возвращается то, что изменилось после бэкапа. Подробнее — `shared/README.md`.
- Хранилище сервера — одна таблица `records(entity, id, fields, clocks, seq)`: сервер сливает и раздаёт
  строки, но не делает запросов по полям, поэтому новая колонка в сущности не требует миграции.
- На клиенте — **outbox** неотправленных изменений; запись удаляется только после ответа 200.
- Триггеры синхронизации: старт, возврат в приложение, таймер, debounce ~2 с после изменений.

### 6.3. Общие фикстуры

Слияние реализовано трижды (Python, TypeScript, Swift). Поэтому `shared/sync-fixtures/*.json` —
тест-кейсы «состояние + изменения → ожидаемый результат», прогоняются во всех трёх реализациях.
Обязательные кейсы: конкурентные правки разных полей, «два обеда», «двойной автоперенос»,
две версии рутины с одной датой, tombstone против правки.

## 7. iOS: виджеты и Live Activity

### 7.1. Общий код и данные

Приложение и расширение виджетов (`SDVGWidgets`) используют один модуль `SDVGCore`
(DB, Sync, Domain) и **одну БД GRDB в App Group-контейнере** (WAL). Отдельной копии данных
у виджета нет — он читает ту же БД и считает «Сейчас» тем же доменным кодом, что и приложение.

- Запись из расширения (кнопка «Готово» в виджете или Live Activity) идёт через тот же слой:
  изменение + HLC + запись в outbox. Отправит её приложение при следующей синхронизации.
- После любых изменений (в приложении, после sync, из интента) — `WidgetCenter.reloadAllTimelines()`
  и обновление активной Live Activity.
- Сеть из расширения не используется: виджет работает офлайн по локальным данным.

### 7.2. Виджеты на главном экране и экране блокировки

| семейство | содержимое |
|---|---|
| `systemSmall` | ближайшая задача + причина (`⏰ через 15 мин`), стрик |
| `systemMedium` | топ-3 «Сейчас» с кнопками «Готово», «выполнено / всего» |
| `systemLarge` | топ-5–7 «Сейчас», стрик, счётчики |
| `accessoryCircular` | кольцо «выполнено / всего» за сегодня |
| `accessoryRectangular` | ближайшая задача и её время |
| `accessoryInline` | `🔥 N · 3/7` — стрик и прогресс |

- **Таймлайн** строится заранее на весь логический день: точки — точное время задач (−30 мин,
  начало, +60 мин — границы окна `now_score`), смены частей суток и смена логического дня
  (`day_start_hour`). Так виджет остаётся актуальным без частых перезагрузок (бюджет iOS ограничен).
- **Интерактивность** (iOS 17+): `Button(intent:)` с `AppIntent` — отметить выполненной
  разовую задачу или рутину. Перенос «на завтра» — только в приложении.
- Тап по виджету — deep link на задачу или экран «Сейчас».

### 7.3. Live Activity

Показывает **текущую задачу с точным временем и длительностью** на экране блокировки и в Dynamic Island:
эмодзи, название, обратный отсчёт до конца (`Text(timerInterval:)`), кнопка «Готово» (`LiveActivityIntent`).

- **Старт** — локально: вручную кнопкой «Начать» на задаче, либо автоматически при открытии приложения
  или фоновом обновлении, если задача с точным временем как раз идёт. Одна активность одновременно.
- **Обновление** — локально из приложения/интента; `staleDate` = конец задачи.
- **Завершение** — при отметке «Готово» (с любого устройства — после sync), по окончании
  длительности или при смене логического дня.
- Push-обновления (APNs, push-to-start) в MVP не используются: backend не отправляет пуши.
  Это ограничивает автостарт — без открытия приложения активность сама не появится.
