# Архитектура СДВГ-трекера

Аналог Tiimo для людей с СДВГ. Один пользователь, клиенты iOS и Web, backend на Python.
Без ИИ и трекера настроения в MVP (автоподбор эмодзи — отдельный этап).

## 1. Принципы

- **Local-first.** Каждый клиент хранит полную копию данных в локальной БД и работает только с ней.
  Сервер — точка синхронизации и бэкап, а не источник истины для UI.
- **Производные данные не храним.** Стрик, счётчики, число переносов, heatmap вычисляются из фактов.
  Хранимый счётчик, увеличенный на двух офлайн-устройствах, неизбежно разъедется.
- **Детерминированные ID** там, где два устройства могут независимо создать «одно и то же»
  (отметка рутины за день, автоперенос за день) — дубли сливаются в одну запись.
- **Неизменяемые сущности** (версии рутин, переносы) — только добавление, конфликтов нет.

```
┌─────────────┐        ┌──────────────┐
│ iOS (Swift) │        │ Web (Vue/PWA)│
│ SQLite/GRDB │        │  IndexedDB   │
│  + outbox   │        │   + outbox   │
└──────┬──────┘        └──────┬───────┘
       │  POST /api/sync (push+pull) │
       └──────────┬──────────────────┘
           ┌──────▼──────┐
           │  FastAPI    │
           │ SQLite (WAL)│  docker compose
           └─────────────┘
```

## 2. Время и дни

- Даты задач — **локальные** `YYYY-MM-DD`, время — локальное `HH:MM`, без таймзоны.
- **Логическое «сегодня»** = `now − day_start_hour` (по умолчанию 4:00): в 1 ночи ещё «вчера».
- Части суток: `morning` / `day` / `evening`, границы настраиваются (по умолчанию 6 / 12 / 18).
- Тип времени задачи `time_kind`: `none` (в любое время) | `part` (часть суток) | `exact` (точное время).
- Порядок дня: «в любое время», затем Утро → День → Вечер; внутри — точное время по времени,
  остальное по `sort_key` (дробный индекс).

## 3. Модель данных

### 3.1. Регулярные задачи (рутины)

Рутина — это **шаблон**. Экземпляры на день не хранятся, а вычисляются.

| сущность | поля | синхронизация |
|---|---|---|
| `routine` | `id`, `sort_key` | LWW по полям |
| `routine_version` | `id`, `routine_id`, `effective_from`, `title`, `emoji`, `color`, `time_kind`, `part_of_day`, `time`, `duration_min`, `weekdays` (битовая маска, по умолчанию все), `archived` | неизменяемая |
| `routine_check` | `id = uuidv5(routine_id + date)`, `routine_id`, `date`, `status` (`done` / `skipped`), `done_at`, `snapshot` {title, emoji, color, time_kind, part_of_day, time} | LWW по полям |

- **Рутины дня D**: для каждой рутины берём версию с максимальным `effective_from <= D`
  (при равенстве — с большим HLC). Если она не `archived` и день недели входит в `weekdays` — рутина есть в дне D.
- **Изменение** создаёт новую версию с `effective_from = сегодня`
  (или завтра, если сегодня рутина уже отмечена). Прошлые дни не меняются.
- **Удаление** — новая версия с `archived = true`. История остаётся.
- **Рутины не переносятся.** Невыполненная рутина прошлого дня — пропуск в истории.
- `skipped` — осознанный пропуск (болезнь и т.п.), не ломает стрик.
- `snapshot` фиксирует, как рутина выглядела в момент отметки.

### 3.2. Разовые задачи

| сущность | поля | синхронизация |
|---|---|---|
| `task` | `id` (UUIDv7), `title`, `notes`, `emoji`, `color`, `date` (null = «Входящие»), `first_date`, `time_kind`, `part_of_day`, `time`, `duration_min`, `deadline_date`, `deadline_time`, `done_on`, `deleted`, `sort_key` | LWW по полям |
| `task_move` | `id = uuidv5(task_id + from_date)`, `task_id`, `from_date`, `to_date`, `kind` (`auto` / `manual`) | неизменяемая |

- **Автоперенос.** При старте клиента и при смене логического дня: для каждой невыполненной задачи
  с `date < today` создаётся **по одной `task_move` на каждый пропущенный день**, затем `date = today`.
  Детерминированный ID — два устройства создадут одинаковые записи, двойного счёта нет.
- **Ручной перенос** («на завтра») — `task_move` с `kind = manual`.
- **Счётчик переносов** = `count(task_move where task_id = …)`.
- **Дедлайн** не сдвигается переносами.

Уровни внимания по переносам (пороги настраиваемые):

| переносов | вид |
|---|---|
| 0 | ничего |
| 1–2 | серый бейдж `↻N` |
| 3–5 | оранжевый бейдж и обводка |
| 6–9 | красный, лёгкая пульсация, поднимается выше в списках |
| 10+ | красный + подсказка «Застряла? Разбить / во Входящие / удалить» |

Индикатор дедлайна: 🟢 ок · 🟡 скоро (≤ 2 дней или прошло > 80 % срока от создания) · 🟠 сегодня · 🔴 просрочен.

### 3.3. Настройки

`settings` — синхронизируемый синглтон (LWW по полям): `day_start_hour`, границы частей суток,
пороги внимания, `streak_min_done` (по умолчанию 1).

### 3.4. Эмодзи и цвет

`emoji` — строка; `color` — индекс в палитре (~12 цветов), одинаковой на iOS и Web и адаптированной
под тёмную тему. Отображение: цветной кружок с эмодзи.

## 4. Производные данные

- **Выполнено за день D** = разовые задачи с `done_on = D` (включая удалённые) + `routine_check` со `status = done` за D.
- **Стрик** — число дней подряд, где выполнено ≥ `streak_min_done`, или все запланированные рутины `skipped`.
  Незавершённое сегодня стрик не обнуляет.
- **Счётчики**: сегодня «выполнено / всего», всего выполнено за всё время.
- **Heatmap** (как на GitHub): 53 недели × 7 дней, 5 уровней; пороги уровней — квантили личной истории.
  Тап по клетке — список задач дня.

## 5. Домашний экран «Сейчас»

Топ 5–7 задач (разовые + рутины сегодняшнего дня) по баллу:

```
score = now_score + deadline_score + postpone_score
now_score:      точное время в окне [−30 мин, +60 мин] → 100; текущая часть суток → 50
deadline_score: просрочен 90 · сегодня 80 · скоро 60
postpone_score: min(переносы × 8, 70)
```

Каждая карточка показывает причину: `⏰ через 15 мин`, `🔥 дедлайн завтра`, `↻ 7 переносов`.

## 6. Синхронизация

### 6.1. Часы

Каждое изменение поля помечается **HLC** (hybrid logical clock): строка
`"{ms:013d}-{counter:04d}-{node_id}"`, лексикографически сортируемая. Для каждой строки хранится
`clocks: {field: hlc}`. Слияние — по каждому полю побеждает максимальный HLC.

### 6.2. Протокол

```
POST /api/sync
Authorization: Bearer <token>
{ "cursor": 1842,
  "changes": [ { "entity": "task", "id": "…",
                 "fields": { "title": "…" }, "clocks": { "title": "…" } } ] }
→
{ "cursor": 1857, "changes": [ …всё, что изменилось на сервере после 1842… ] }
```

- Сервер ведёт монотонный `server_seq`; каждое изменение строки получает новый seq. Pull: `seq > cursor`.
- Push идемпотентен (слияние по HLC), всё в одной транзакции.
- На клиенте — **outbox** неотправленных изменений; запись удаляется только после ответа 200.
- Триггеры синхронизации: старт, возврат в приложение, таймер, debounce ~2 с после изменений.

### 6.3. Общие фикстуры

Слияние реализовано трижды (Python, TypeScript, Swift). Поэтому `shared/sync-fixtures/*.json` —
тест-кейсы «состояние + изменения → ожидаемый результат», прогоняются во всех трёх реализациях.
Обязательные кейсы: конкурентные правки разных полей, «два обеда», «двойной автоперенос»,
две версии рутины с одной датой, tombstone против правки.

## 7. Стек

| часть | технологии |
|---|---|
| Backend | Python 3.12, uv, FastAPI, SQLAlchemy 2, Alembic, SQLite (WAL), pytest |
| Web | Vue 3, Vite, TypeScript, Pinia, Dexie (IndexedDB), vite-plugin-pwa, Vitest |

## 9. Вне MVP

- Автоподбор эмодзи: многоязычные эмбеддинги (например, `multilingual-e5-small`) + ближайшее
  описание эмодзи; сервер `/api/suggest-emoji`, transformers.js в вебе, Core ML на iOS; офлайн-фолбэк — словарь.
- Подзадачи, заморозка стрика, виджеты / Live Activity.
