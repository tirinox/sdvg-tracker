# Общие контракты

Всё, что должно одинаково работать в трёх реализациях: backend (Python), web (TypeScript),
iOS (Swift). Любое изменение здесь — изменение контракта: обновите фикстуры и все реализации.

```
schema/           JSON Schema сущностей и протокола синхронизации
vectors/          тест-векторы HLC и детерминированных ID
sync-fixtures/    тест-кейсы слияния изменений
domain-fixtures/  тест-кейсы доменной логики (дни, рутины, переносы, стрик, «Сейчас»)
```

## Сущности

| сущность | схема | изменяемость |
|---|---|---|
| `task` | `schema/task.schema.json` | изменяемая |
| `task_move` | `schema/task_move.schema.json` | неизменяемая |
| `routine` | `schema/routine.schema.json` | изменяемая |
| `routine_version` | `schema/routine_version.schema.json` | неизменяемая |
| `routine_check` | `schema/routine_check.schema.json` | изменяемая |
| `settings` | `schema/settings.schema.json` | изменяемая, синглтон с `id = "settings"` |

- `id` — UUID в нижнем регистре. Случайные ID — UUIDv7 (генерирует клиент), детерминированные — UUIDv5 (ниже).
- Схема описывает **полную строку** (все поля обязательны). В изменении (push) может быть любое подмножество полей.
- Строки физически не удаляются: у `task` есть поле `deleted`, рутина удаляется версией с `archived = true`.
- Неизменяемость — соглашение клиентов: такие строки только создаются. Сервер и слияние обрабатывают все
  сущности одинаково.
- `time_kind` — источник истины для времени: `part_of_day` учитывается только при `part`,
  `time` — только при `exact`. После слияния остальные поля могут содержать устаревшие значения — это нормально.
- Даты (`YYYY-MM-DD`) и время (`HH:MM`) — локальные, без таймзоны. `*_at` — моменты в UTC (`...Z`).

## HLC (гибридные логические часы)

Формат: `{l:013d}-{c:04d}-{node_id}`, например `1790000000000-0003-a1b2c3d4e5f60718`.

- `l` — логическое время в мс, `c` — счётчик, `node_id` — 16 hex-символов, случайный на установку клиента
  (у сервера свой `node_id`).
- Сравнение — **обычное сравнение строк**.
- Локальное событие при физическом времени `pt`:
  `pt > l` → `l = pt, c = 0`; иначе `c += 1`.
- Получение удалённой метки `(rl, rc)`: `l' = max(l, rl, pt)`;
  `l' == l == rl` → `c = max(c, rc) + 1`; `l' == l` → `c += 1`; `l' == rl` → `c = rc + 1`; иначе `c = 0`.
- Переполнение: если `c > 9999`, то `l += 1, c = 0`.

Тест-векторы: `vectors/hlc.json`.

## Слияние

Строка хранит `fields` и `clocks` (HLC для каждого поля). Изменение `{entity, id, fields, clocks}`
применяется по каждому полю: значение записывается, если поля ещё нет или `clock > clocks[field]`.
Неизвестный `id` создаёт строку. Результат не зависит от порядка и повторов изменений.

Формат `sync-fixtures/*.json`:

```json
{ "description": "…",
  "cases": [ { "name": "…", "description": "…", "order_independent": true,
               "initial": [row], "changes": [change], "expected": [row] } ] }
```

`row` и `change` имеют один формат `{entity, id, fields, clocks}`. `expected` отсортирован по `(entity, id)`.
Если `order_independent`, реализация должна получать `expected` при любом порядке `changes`.

## Протокол `/api/sync`

`POST /api/sync`, заголовок `Authorization: Bearer <token>`. Схемы — `schema/sync.schema.json`
(`#/$defs/request`, `#/$defs/response`).

1. Сервер в одной транзакции применяет `changes` по правилам слияния. Каждая изменённая строка получает
   новый монотонный `server_seq`.
2. Возвращает полные строки с `server_seq > cursor` (включая только что отправленные клиентом),
   не больше `limit`, по возрастанию `server_seq`. `cursor` в ответе — `server_seq` последней строки
   (или прежний, если строк нет). `has_more = true` — клиент повторяет запрос с новым курсором.
3. Клиент применяет ответ по тем же правилам слияния, сохраняет курсор и удаляет из outbox
   отправленные изменения — только после успешного ответа.

Повтор запроса безопасен: слияние идемпотентно.

## Доменные фикстуры

Формат `domain-fixtures/*.json`: `{ "description": правило, "cases": [ { name, input, expect } ] }`.
Правило в `description` — нормативное; `input` и `expect` различаются по файлам.
Heatmap-уровни (квантили) будут добавлены на этапе 2.
